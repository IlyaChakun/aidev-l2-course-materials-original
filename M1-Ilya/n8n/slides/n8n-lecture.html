Part 1 · What a workflow is

A workflow is a process written down: a trigger, steps, rules, and an execution engine that tracks runs, manages state, and supports recovery according to its capabilities and configuration

Triggeran event starts a run: a webhook, a schedule, a new email, a chat message
Stepscalls to systems and data transforms: read a ticket, call an API, write a row
Rulesbranches, waits and approvals: if the amount is over the limit, ask a manager
Run logevery run is saved with its data: you see where it failed and retry from there
Kind of engineExamplesWho builds itTypical job
Integration automationZapier, Make, Power Automate, n8nops, analysts, developers; visualglue between SaaS and internal systems, now with AI steps
Business processes (BPMN)Camunda, Flowablean analyst draws, developers implementlong processes with people in them: a loan approval, onboarding
Durable executionTemporal, AWS Step Functionsdevelopers, in codebackend processes that must survive crashes: payments, orders
Data pipelinesAirflow, Dagster, Prefectdata engineers, in codescheduled batch jobs: load, clean, aggregate
In practiceAn engine, not a script, gives you retries, waits for hours or days, a log of every run, and a process that someone other than its author can read and change.

Part 1 · Workflow or agent

If you can name the steps, it's a workflow; if you can't, it's an agent

Each step up the ladder gives the model more freedom, and costs more: tokens, time, and tests that can't check one exact answer. So every part of a process goes on the lowest step that can handle it.

1 · Rule

IF or Switch: code decides

the amount is over the limit → ask a manager

2 · Classifier

the model picks one label from a fixed list

a ticket → billing, account or bug

3 · AI Agent

the model picks which tools to call, and in what order

read the ticket, look up the account, answer or escalate

4 · Code, LangGraph

loops, state, long processes

beyond the canvas

predictable, cheap, exact testsflexible, costly, scored tests
if you can name out the steps, then it's for a workflow… If you can't name those steps… then it's an agentLiam McGarrigle, n8n · livestream “The Agent Left the Workflow”, 2026
it's much cheaper to use a simple if … and is 100% reliableJan Oberhauser, n8n · Product Growth podcast, 2026
In practiceThe ticket chain at the end of this session is a workflow with two agent steps, not one big agent: the steps around them can be named.

Part 1 · Product goal

Product goal: glue between systems that you can see and change, without SaaS lock-in or your own plumbing

Zapier, Make

  • closed SaaS, nothing to host;
  • code only inside the vendor's sandbox;
  • no hosting next to your own data.

Your own code

  • as flexible as you want;
  • all the plumbing is yours: auth, retries, pagination;
  • usually only its author maintains it.

n8n

  • a visual editor for the flow;
  • JavaScript or Python in a Code node;

Part 2 · Building blocks

Most of a workflow is triggers, integrations and logic; AI nodes are a few boxes among them

Triggers

Start a run: Webhook, Schedule, Form, Chat, an app event (a new row, a new email), MCP Server Trigger.

A workflow can have several.

Action nodes

2,000+ integrations: Slack, Jira, Postgres, Google Sheets. For anything else, HTTP Request.

Each one is a typed API call with auth built in.

Logic nodes

IF, Switch, Merge, Loop Over Items, Wait, Execute Workflow for sub-workflows, Code for JavaScript or Python.

Rules live here, not in a prompt.

Expressions

Any parameter can take data from earlier nodes: {{ $json.email }}, {{ $('Classifier').item.json.category }}.

The glue between nodes.

Credentials

Keys and OAuth tokens are stored once, encrypted with N8N_ENCRYPTION_KEY, and picked by name in a node.

The workflow JSON holds only a reference.

Executions

Every run is saved with each node's input and output. A failed run can trigger an error workflow.

Kept 14 days or up to 10,000 runs by default.

Part 2 · Running it

On a laptop n8n is one process; in production it's a queue and workers you can add

Regular mode · the default

One process serves the editor, listens to triggers and runs every execution. Enough for a laptop or a small team.

The catch: by default nothing limits how many runs it takes at once, and they all share that one process.

Queue mode · for production

The main process only accepts work and puts it in a queue; workers run it. Add workers to take more load.

Needs Redis as the broker and Postgres as the shared database; SQLite isn't recommended here.

  1. A trigger fires: a webhook, a timer, a chat message
  2. main stores the execution and puts its id in Redis
  3. A free worker takes it and runs the workflow10 executions at a time per worker by default
  4. The worker writes each node's data to Postgres; the editor shows it from there
In practiceStart in regular mode. Switching isn't a flag: you add Redis, move from SQLite to Postgres, share the key and run workers.

Part 2 · Memory

An agent forgets everything between runs; a memory node reloads the last few exchanges stored under a session key

One agent run with memory

  1. Load the history for this session keythe last 5 exchanges by default: 10 messages
  2. Build the prompt: system prompt + history + the new inputthe system prompt isn't stored; it's rebuilt every run
  3. Run the agent loop and its tools
  4. Save the user message, the tool calls with their results, and the answertool messages count toward the 10, so they push old turns out
Memory nodeWhere the history lives
Simple Memoryinside the n8n process: lost on restart, dropped after an hour idle, doesn't work in queue mode
Postgres, Redis, MongoDB Chat Memoryyour database: a table or collection n8n_chat_histories; Redis can expire sessions
Chat Memory Managernot a store: reads, inserts or deletes messages, to clear a session or write a summary yourself

Session key. With a Chat Trigger it's the chat's sessionId. With any other trigger, set it yourself: a user, thread or ticket id. A constant key gives every user one shared history.

In practiceMemory is chat history, not knowledge: facts that must last go into a database or a vector store the agent reads through a tool.

Part 2 · Testing 2 of 4

Mock the model to test the wiring; to test its answers, climb from a vibe check to an LLM judge

Three ways to handle the model in tests

  1. Pin the agent's output. The next nodes get a fixed answer.for debugging, manual runs only
  2. A fake model behind the Base URL. A small OpenAI-compatible server returns scripted replies; no key, no tokens.for CI: checks connections, tool calls, parsers, not quality
  3. The real model, same inputs, several runs. The answer varies from run to run.before a release, or after a prompt change

Three kinds of checks on the answers

  1. Vibe check. Use it yourself: chat with the agent, feed the classifier real inputs.not automated; it shows what to check automatically later
  2. Deterministic checks. Were the tools called? Is the category right? Did retrieval find the right documents?a yes or no per case; no model needed to judge
  3. An LLM as a judge. Does the answer say what the reference answer says?for free text, where no exact match exists
traditional testing… really assumes that your workflow is deterministic, right?JP van Oosten, n8n · “Evaluations in Agentic Workflows”, 2025
In practiceA mock checks the wiring and needs no model; checks 2 and 3 need the real model and a dataset: that's n8n Evaluations.

Part 2 · Testing 3 of 4 · Evaluations

n8n Evaluations run the workflow over a dataset, one row at a time, and score each answer, so a prompt change becomes a number

Data Table or Sheetinput + expected→ Evaluation Triggerone row per run→ Edit Fieldsrow → input→ your workflow→ Set Outputsanswer → the row→ Set Metricsscores
MetricWhat it scores
Correctnessan LLM judge: does the answer match the reference? 1–5
Helpfulnessan LLM judge: does it answer the question? 1–5
Categorizationthe output equals the expected category: 1 or 0
String Similarityhow close the text is to the expected one: 0–1
Tools Usedthe share of expected tools the agent called: 0–1
Customany number you compute, even in another workflow

What you get

  • the Evaluations tab: one line per run, the average of each metric, tokens and run time
  • a click from any row to its execution, to see why it scored low
  • Check If Evaluating: a branch that skips side effects, like sending an email, in eval runs
  • the judge's prompt is editable: you decide what a 5 and a 4 mean

Plan: running the dataset and writing outputs back: every plan, free self-hosted after you register the instance. Metrics: one workflow on free and Starter, unlimited on Pro and above.

In practiceSame dataset, one change at a time: the metric shows whether the change helped.

Part 2 · Testing 4 of 4 · When to run evals

Run evals while you build, before you release, and in production, because models and users change under you

1 · While you build

  • the whole dataset after every prompt edit, not one chat
  • edge cases from day one: empty values, odd formats
  • fix the cases that break, then rerun

2 · Before you release

  • A/B two models or prompts: a dataset column picks the model through a Model Selector node
  • weigh quality against tokens and run time

3 · In production

  • catch regressions: cases that used to pass
  • copy real cases from executions into the dataset
  • rerun when a new model comes out: does it help or break?
One dataset, three prompt versions, average Correctness: 4.2→3.4the prompt added “answer like a pirate, with a parrot joke”→4.8

The judge is a model too

It needs a reference answer to compare with. Its scores vary: try to fool it on purpose before you trust it, and repeat a case several times.

Keep the dataset frozen

If a step reads live data, like a stock price, the expected answer goes stale. Feed that step a fixed copy during evals.

In practiceEach bad answer from production becomes a new row in the dataset.

Part 2 · To production

A workflow reaches production through Git and a review, not through edits in the production editor

Before
one instance for everything→workflows copied into a “prod” folder→bugs fixed straight in proddev falls behind, copies multiply, no versions, no backups
After
dev instanceits own credentials→ push →Gitpull request and review→ pull →prod instanceprotected: nobody edits it
we started to just hot fix everything in productionBach-Thi Dinh, Exxeta · “Test & Production Deployment in n8n”, 2025

What travels through Git

  • workflows with tags, folders, projects
  • credentials and variables as stubs: the name and type, no values
  • Data Table schemas, without rows

What n8n won't do for you

  • merge: two people's changes to one workflow can't be combined
  • detect conflicts: a pull overwrites local changes, a push overwrites Git
  • review: it happens in GitHub or GitLab, not in n8n

Environments: Business and Enterprise, self-hosted. On free n8n: n8n export:workflow → Git → n8n import:workflow on the second instance.

In practiceChanges go one way: dev → Git → prod. A bug is fixed in dev and shipped again.

Part 2 · Testing with one endpoint

Slack sends an app's events to one URL; to test without touching prod, give each environment its own sender or replay real events

The problemThe Slack app's Request URL points at prod n8n, so dev and test never see a real event. Telegram bots and WhatsApp have the same limit.
OptionHowCost and risk
A Slack app per environmentclone the app from its manifest; dev, test and prod each get their own app, channel and credentialsfree; more apps to keep in sync
A second workspace, called “test”a separate Slack workspace and a separate HubSpot account, each with its own webhooksExxeta paid for them; Slack sandboxes and HubSpot test accounts are free now; data has to be seeded
A router workflow with a switchone workflow takes every webhook and only routes; in test mode it also sends a copy to test sub-workflows, or a mock in place of the real callfree, live data; but test runs on the prod instance, and the router becomes a single point of failure
Record and replaytake a real event from a past execution; pin it on the trigger or open it with Debug in editor; or POST it to the test webhookfree, no risk; the event is frozen, not live
Swap the URL by handunpublish, set the test URL in Slack, test, put the production URL back, publishfree; prod hears nothing while you test
In practiceReplay recorded events day to day; when you need live events, give test its own sender, not a branch in prod.

Part 4 · Our example

Example system: support triage. A ticket comes in; two agents sort it and answer it or escalate it

The taskA support desk gets tickets. Someone has to read each one, set a category and priority, then answer it or pass it on.
Ina ticket number from the chat. The ticket itself lives in the ticket system: the MCP server from the first half of this session.
Outthe ticket in the database: a category, a priority and status answered, or an escalation with the reason.
In practiceEach agent gets one job and only the tools it needs: the Classifier reads and sorts, the Operator reads and writes. Code nodes between them catch bad JSON.
