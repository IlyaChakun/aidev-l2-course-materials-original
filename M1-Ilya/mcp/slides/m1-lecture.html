Part 1 · When to use it

MCP is one way to connect an agent to a system, not the only one

MCP pays off when

  • the model decides which tools to call, and when;
  • one server has several consumers: Claude Code, Cursor, an n8n agent;
  • you want one place for the contract and the access rules.

You may not need it when

  • the steps are fixed: call the API from code;
  • the agent loop and the API are both yours, with one consumer;
  • a skill or a CLI already does the job.
If it's predetermined, then you probably don't need to use a tool.Mahesh Murag, Anthropic · “Building Agents with Model Context Protocol”, 2025

Revision 1 of 5 · 2024-11-05 · Launch

It starts local: one protocol, servers on your own machine

WhyEvery AI app needed its own integration for every tool.
  • added
    stdio transport

    The app launches the server as a local process. Still the default for local servers.

  • added
    Tools, resources, prompts

    Three primitives with three owners: the model, the application, the user.

  • added
    A stateful connection with an initialize handshake

    Both sides agree once on a version and features. Removed in 2026.

  • not yet
    Authorization

    Servers ran on the user's machine; nobody to keep out. OAuth came next.

Homework: the starter server follows this model: stdio, tools and resources.

Revision 2 of 5 · 2025-03-26 · Going remote

Servers move to the network, so the protocol needs real HTTP and auth

WhyThe first remote transport, HTTP+SSE, needed an always-on connection that couldn't resume after a drop. And anyone could call a remote server.
  • added
    Streamable HTTPPR #206

    One endpoint, plain POST requests, streaming only when needed. Replaces HTTP+SSE.

  • added
    OAuth 2.1 authorizationPR #133

    A server on the network has to know who is calling.

  • added
    Tool annotations: readOnlyHint, destructiveHint, …PR #185

    Let a client ask before a destructive call. Hints, not guarantees.

  • added
    JSON-RPC batchingPR #228

    Allowed by JSON-RPC 2.0. It lasted three months.

Homework: the advanced level, Streamable HTTP with a bearer token, comes from here. Good practice, not a requirement: mark get_* and list_* tools read-only.

Revision 3 of 5 · 2025-06-18 · Growing up

Contracts get stricter: typed results, questions to the user, safer tokens

WhyTools returned free text, servers couldn't ask the user anything, and a malicious server could get hold of a token meant for another one.
  • added
    Structured tool outputPR #371

    outputSchema + structuredContent: results the client can validate.

  • added
    ElicitationPR #382

    The server asks the user for missing input mid-call.

  • changed
    Tokens bound to one server (RFC 8707)PR #338, #734

    Servers check tokens, they don't issue them; each token names the server it's for.

  • removed
    JSON-RPC batchingPR #416

    The author saw no compelling use cases. Gone after three months, with no warning.

Homework: your error payload follows the same idea: fixed fields the model can rely on, not a sentence to parse.

Revision 4 of 5 · 2025-11-25 · One year of MCP

A year in: errors the model can read, long-running work, registration by URL

WhyLong tool calls could vanish without a trace, models never saw why their arguments were rejected, and every server kept a growing database of clients.
  • changed
    Invalid input is a tool error, not a protocol errorSEP-1303

    A tool result with isError reaches the model, so it can fix its call.

  • experimental
    TasksSEP-1686

    Start long work now, fetch the result later.

  • added
    Client ID Metadata DocumentsSEP-991

    An HTTPS URL is the client ID: no registration database.

  • added
    URL mode elicitationSEP-1036

    Secrets go into a web page, never through the client or the model.

Homework: a forbidden status change must list the allowed transitions; return it as a tool result with isError, the same idea as SEP-1303.

Revision 5 of 5 · 2026-07-28 · Stateless · current

Stateless: every request carries everything it needs

WhySessions tied each client to one server instance: sticky routing, per-client cleanup, lists you couldn't cache.
  • removed
    Sessions, the handshake, ping, SSE resumabilitySEP-2567, 2575

    Any instance behind a plain load balancer can serve any request.

  • added
    MRTR: Multi Round-Trip RequestsSEP-2322

    The server answers input_required; the client retries the call with the answers.

  • deprecated
    Sampling, roots, protocol-level loggingSEP-2577

    Sampling and roots: few clients implemented them. Logging duplicates stderr and OpenTelemetry.

  • extension
    Tasks move out of the core (Beta)SEP-2663

    The first design leaned on sessions; Tasks were reworked as an official extension.

  • added
    A deprecation policySEP-2596

    Normally at least twelve months' notice before a feature goes. Batching vanishing in one release is one of the cases it cites.

Homework: keep ticket state in the database, not in the server process.

Part 3 · The diagnosis

Most bad MCP servers are a REST API with a new label

Humans don't use APIs. Humans use products.Jeremiah Lowin, Prefect · “Your MCP Server is Bad”, 2025

A REST API is built for a developer who reads the docs once and writes a script. An agent rediscovers your server on every connection and decides each step on the fly.

We all need to stop taking REST APIs and put them one-to-one into an MCP server.David Soria Parra, Anthropic · “The Future of MCP”, 2026
In practiceDesign tools around what the agent needs to get done, not one tool per endpoint.

Part 3 · Why it matters

An agent pays for every tool, every turn and every token

A developer with a REST APIAn agent with MCP
Discoveryreads the docs oncereads every description on every connection, in tokens
Iterationa script calls known routeseach call is a model turn; the history is read again
Contextremembers what it learneda finite window that tool descriptions fill up
An agent can find a needle in a haystack. The problem is it's going to look at every piece of hay and decide if it's a needle.Jeremiah Lowin, Prefect · “Your MCP Server is Bad”, 2025
In practiceFewer tools, each doing more, each described well. The next five slides show how.

Part 3 · Rule 1 of 5

Expose outcomes, not operations

Operations: three tools, three turns

get_user(email)        → user_id
get_orders(user_id)    → [order_id, …]
check_status(order_id) → status

The agent guesses the order and carries IDs between calls.

Outcome: one tool, one turn

track_latest_order(email)
  → {order_id, status, eta}

The same three API calls, inside the tool, in code.

In smart-support, three tools cover the whole ticket lifecycle: list_tickets, get_ticket, update_ticket. Not one tool per field or per status.

Part 3 · Rule 2 of 5

Make names, arguments and examples hard to misread

DoDon'tWhy
Namesverb + object: update_ticketrunThe model matches requests against names first.
Argumentsflat, with enums and defaultsconfig: dictFewer free-form fields, fewer wrong guesses.
Examplesrealistic and variedone narrow exampleThe model copies examples literally.
If your example has two tags, you will never get 10 tags. You will get two tags pretty much every time.Jeremiah Lowin, Prefect · “Your MCP Server is Bad”, 2025

It happened to us

The agent passed agent="operator" on every call, because that's what the example in the update_ticket description said.

Part 3 · Rule 3 of 5

A tool description is a prompt: write it like one

  1. What it does
  2. When to call itand what to call first
  3. When not to call itas a redirect, not a bare “don't”
  4. Input and outputincluding what a rejection looks like
  5. An example
# update_ticket, excerpt
Allowed status transitions (the server
enforces them, you cannot bypass them):
  new -> answered, new -> escalated,
  answered -> escalated.
  'escalated' is final.

When NOT to call: to read data
(use get_ticket or list_tickets);
when the ticket is already 'escalated'
(nothing can change it, report that
and stop).
In practiceEvery “when not to call” line also says what to do instead.

Part 3 · Rule 4 of 5

Errors are prompts too: say what's wrong and what to do next

A bare ValueError tells the model nothing. A good error has four fields the model acts on:

codea stable name to match on
current_statuswhere the ticket is now
allowed_transitionswhat is possible from here
hintwhat to do next, in plain words
{
  "ok": false,
  "error": {
    "code": "INVALID_STATUS_TRANSITION",
    "message": "cannot move ticket 5 from
      'answered' to 'new'",
    "hint": "Ticket 5 is 'answered'. Retry
      update_ticket with new_status in
      ['escalated'], or stop if none fits.",
    "current_status": "answered",
    "allowed_transitions": ["escalated"]
  }
}
In practiceThe error helps the agent recover. The code still blocks the forbidden change.
DEMO 1 · A/B

A good error lets the agent fix itself

Same request to both servers“Ticket 12 was answered by mistake. Use the support-tickets server to move it back to new.”

Setup

Two copies of one server, with the status graph removed from descriptions, instructions and resources. Only the error differs.

A answers every rejection with {"error": "Invalid transition"}.

B answers with the error from the previous slide.

Watch for

  • what each agent tells you after the rejection;
  • whether it finds the one allowed move or gives up.

What it proves

Both servers knew why they refused. Only B said so, and only B's agent could act on it.

Part 3 · Rule 5 of 5

Keep the tool count low: the limit is per agent, not per server

  • Lowin's rule of thumb: 5–15 tools. Around 50 per agent is where it starts to hurt.A heuristic from practice, not a measurement.
  • An agent connected to two servers with 50 tools each sees 100.
  • A Fivetran engineer cut his own MCP server from 188 tools to 5.Kelly Kohlleffel, as told by Lowin, Nov 2025.
  • Clients help: Tool Search loads descriptions on demand, 56,000+ tokens down to about 9,000.David Soria Parra, Anthropic · slide in “The Future of MCP”, 2026. It helps, but it won't save a server with 188 tools.
  • Code execution: the agent writes a script that calls the tools, and only the result reaches the model. 150,000 tokens down to 2,000 in Anthropic's example.Anthropic, “Code execution with MCP”, Nov 2025; Cloudflare calls it Code Mode. A client-side pattern: your server still needs good tools.

DEMO 3 · CLAUDE CODE

An agent with no hints follows the lifecycle and recovers from a rejection

Steps

  1. Find the waiting tickets, then answer ticket 5
  2. Ask for update_ticket to move ticket 5 back to new

Use the official 2.x SDK, and don't mix it with fastmcp

LanguageInstallThe trap

Old recipes

mcp.server.fastmcp is 1.x. In 2.x: from mcp.server import MCPServer.

stdout is sacred

On stdio, one stray print() breaks the protocol. Log to stderr.

Inspector 2.12.0+

Use 2.12.0 or later: older versions have remote code execution flaws.

Part 5 · Security

A badly designed MCP server is also a badly secured one

RiskWhat goes wrongWhat you do
Tool poisoningDescription text goes straight into the model's context.Read a third-party server's descriptions before connecting it.
Hints taken as rulesNothing enforces readOnlyHint.Enforce read-only in the server.
OversharingPII, keys and internal IDs end up in the context.Return only what the task needs.
Local → remoteOAuth, TLS, CORS, rate limits arrive at once.Plan for them before leaving stdio.
Open supergatewayNo auth: anyone on the network can call your tools.Run it only for the test.

The title is a line from Tun Shwe and Jeremy Frenay, Lenses · “Your Insecure MCP Server Won't Survive Production”, 2026. The full topic is module 7.

Part 5 · At company scale

A gateway puts sign-in, access rules and audit in one place

One sign-in

Without: every server has its own OAuth.

With: one sign-in via the company's identity provider.

Access rules

Without: each server decides, or nobody does.

With: one policy: who may call which server and tool.

Audit

Without: logs in four places, four formats.

With: one log of every call, in one format.

The registry (official MCP Registry, preview since 8 Sep 2025) is a catalog, not a security review: read an unknown server's descriptions in Inspector before you connect it.

In practiceA single homework server doesn't need a gateway. A company with fifty servers does.
