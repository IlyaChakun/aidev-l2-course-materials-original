Missed what was needed

Recall in information retrieval: the share of all relevant documents the search found. The homework's recall@5 is narrower: is the expected document in the top 5?

Measuring search is older than embeddings. The Cranfield experiments (1960s) first scored retrieval against questions with known answers; TREC, the yearly US retrieval benchmark, has done it since 1992. The recipe is the one in your homework: questions plus the documents that answer them.

Search / 12 · Inverted index

An inverted index maps each word to its documents, so queries never scan text

Problemscanning every document's text for every query costs time in proportion to the whole corpus
Fixbuild once: for each token, a posting list of the documents that contain it and how often (tf, term frequency)
Resulta query reads only the lists of its own tokens; the price is exact token matching

3 documents, 35 tokens, 25 distinct tokens in the index. The query “Lumen export” reads 2 lists with 4 entries instead of 35 tokens of text; on millions of documents that difference is the whole point.

The same structure sits under Lucene (1999), Elasticsearch (2010), Solr, PostgreSQL full-text search and Qdrant's sparse vectors.

Watch outthe index tells which documents match, not which is best: d0, d1 and d2 all contain “lumen”; ranking is IDF and BM25, next

Search / 14 · IDF

IDF: words in every document weigh almost nothing, words in one document weigh most

Problem“Lumen export” matches all three documents on lumen; counting matched words would rank them almost equally
Intuitionthe fewer documents contain a word, the more it tells you which one you need
FormulaIDF = ln(1 + (N − df + 0.5) / (df + 0.5)): N documents, df of them contain the word
Tokendf, of N = 3IDF
lumen30.134
page20.470
e-4031, export, reset10.981

lumen: ln(1 + (3 − 3 + 0.5) / (3 + 0.5)) = ln(1.143) = 0.134. export: ln(1 + 2.5 / 1.5) = ln(2.667) = 0.981. A rare token weighs seven times more than one in every document.

df = document frequency, IDF = inverse document frequency. IDF counts documents, not repeats: export (5 times in d2) and e-4031 (once in d1) both get 0.981. Repeats are TF, next.

Why this form, not ln(N / df)

ln(3 / 3) = 0 would erase lumen completely. The original Robertson–Spärck Jones weight ln((N − df + 0.5) / (df + 0.5)) turns negative when a word is in more than half the documents: lumen would get −1.95. Lucene and Elasticsearch add 1 inside the log, so every weight stays positive.

terms should be weighted according to collection frequency, so that matches on less frequent, more specific, terms are of greater valueKaren Spärck Jones · “A statistical interpretation of term specificity and its application in retrieval”, 1972

Homework: modifier: idf on the sparse bm25 vector makes Qdrant compute this weight from the collection; without it every word weighs the same.

Watch outrarity is not relevance: a typo like “pasword” is also in one document and gets the same 0.981 as e-4031

Search / 16 · TF and BM25

TF counts repeats, BM25 caps them: the fifth “export” adds far less than the first

ProblemTF·IDF = tf × IDF pays for every repeat: “export” ×1 scores 0.98, ×5 4.90, ×10 9.81. Repeating a word wins, and long documents repeat words just by being long
FixBM25 keeps IDF, passes tf through a curve that flattens (knob k1) and compares the document’s length with the average (knob b)
Result“export” in d2 scores 1.71, not 4.90; no token can pass IDF × (k1 + 1) = 2.16, however often it repeats

score(t, d) = IDF(t) × tf × (k1 + 1) / (tf + k1 × (1 − b + b × dl / avgdl))Okapi BM25, Robertson et al., TREC-3, 1994 · chart: average-length document, Lucene defaults

TermWhat it isHere
tftimes the token occurs in this documentd2: 5
IDFrarity weight, from the IDF slide0.981
k1saturation: 0 = only presence counts, larger = closer to plain TF1.2
blength correction: 0 = none, 1 = full0.75

Vectors / 22 · The bridge

BM25 can't see synonyms: “I can't log in” and “reset password” score zero

Problemafter stop words the two questions share no word, so BM25 gives 0
Fixa dense vector (embedding) encodes meaning: the same pair gets cosine 0.47
Resultdense finds paraphrases but misses exact strings, so every chunk keeps both vectors

BM25(“I can't log in to my account”, “How do I reset my password?”) = 0 once stop words such as I and my are removed, as Qdrant/bm25 does · cosine of their embeddings = 0.47

Sparse vector (BM25)

One position per word in the vocabulary. Almost all zeros; the non-zeros are the document's words.

001.300000.800…

Length = vocabulary size. Matches words exactly.

Dense vector (embedding)

1,024–1,536 numbers, none of them zero; no single number means anything, the direction of the whole vector does.

.079.003.046-.013.051-.011-.004.058…

Length fixed by the model. Matches meaning, across wording and language.

Vectors / 25 · Cosine

Cosine measures the angle between vectors: same direction, similar meaning, whatever the words

Problemthe dot product a · b (multiply the vectors number by number, add up) grows with their length, so it would reward long vectors, not similar meaning
Fixcos = a · b / (|a| × |b|): divide by both lengths and only the angle is left. 1 = same direction, 0 = a right angle, unrelated
Resulta ranking you can compare, but the values are not probabilities

Vectors / 26 · One model

Use one embedding model for writing and searching, and record its name in metadata

Problemtwo models with 1,536 numbers each mix without any error
Fixone model for writing and searching; a new model means a new collection and a reindex

The same size is more dangerous than a different size

text-embedding-ada-002 and text-embedding-3-small both return 1,536 numbers. Mix them and nothing fails: the results just become noise.

Vectors / 27 · Limits

Embeddings break on exact identifiers, outside their training domain and on long texts

Probleman embedding keeps the meaning of the whole text, not its exact characters: “What does E-4031 mean?” becomes “a question about a payment error code”, and every error-code chunk looks alike
Fixnothing inside the vector fixes this; keep a word-based branch next to it: BM25 matches E-4031 character for character (Hybrid chapter)
ResultLab 01, step 3: dense puts the E-4031 chunk 4th, behind the general error list, E-4012 and E-1105; BM25 puts it 2nd

Exact identifiers

An error code, an SKU, a name, a version. E-4031 and E-4012 differ by two characters and land on almost the same spot: in Lab 01 their scores differ by 0.005.

Out of domain

A model knows the senses its training text had. Your product names, internal jargon and abbreviations may be unknown to it or mean something else: in Word2Vec, python is Monty Python, not the language.

Long texts

A model reads a limited number of tokens: text-embedding-3-small up to 8,191. Beyond that the API rejects the text or a library silently cuts it, and the tail never reaches the vector. One vector for a long text also averages several topics into one.

There is also a theoretical ceiling: the number of distinct top-k result sets a single vector can express is bounded by its dimension.

Weller et al., Google DeepMind and Johns Hopkins · “On the Theoretical Limitations of Embedding-Based Retrieval”, the LIMIT dataset, Aug 2025, ICLR 2026.

RRF adds up places, not scores: score = Σ 1 / (k + rank)

CAG / 58 · The border

CAG suits a small, stable, shared corpus; growth, churn or per-user rights favour RAG

Problempicking CAG or RAG by fashion instead of by your data, traffic and prices
Fixcheck both lists against your project
Resultper-user rights alone rule out CAG: one shared prefix cannot be filtered per user

CAG can win when

  • the corpus is small and rarely changes
  • requests are frequent (several a minute), so the cache stays warm
  • the cached read price is low for your provider

RAG wins when

  • the corpus grows or changes often
  • users see different documents: rights are filtered per query
  • cost must not grow with the corpus
  • answers get worse when the fact is buried in a long context

Both can cite: in CAG, keep a source id next to each document in the prefix. The full decision tree is in the Build chapter. Block B asks you to find this border on your own project, with your own numbers.

Appendix / 35 · Silent failures

A successful database response can still contain the wrong evidence

Problemthe database answers successfully, but with the wrong evidence
Fixpin the embedding model, test filters against exact search, log token lengths
Resultrerun recall@5, grounding and trap tests after every ingestion or model change

Wrong embedding space

Two embedding models can produce vectors of the same size but incompatible semantics.

Check: pin model, revision and preprocessing on writes and reads.

Wrong authorised set

Overly restrictive or incorrectly applied filters hide valid documents — or expose forbidden ones.

Check: test ACLs and compare approximate against exact filtered search.

Truncated content

Embedding models may silently truncate long chunks or indexing may lose table structure.

Check: log token lengths, parse quality and retrieved source text.

In practiceTrace source IDs and scores; rerun document recall@5, groundedness and trap tests after each ingestion or model change.

Appendix / 40 · When it pays

Write 1.25× the input price (5-minute TTL, time to live) or 2× (1 hour); read 0.1×, and 0.05× on Claude Opus 5.5 and Sonnet 5.5.
